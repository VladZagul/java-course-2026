# ЛР №4. Реалізація програмних інтерфейсів

**Тема проєкту №14 — система бронювання квитків на автобус.**

## Сутність

`Booking` (бронювання): ім'я пасажира, маршрут, кількість місць, ціна одного місця. Перевірка доменних правил і власні винятки — з ЛР №3 (`DomainException`, `InvalidPriceException`, `InvalidQuantityException`).

Клас `Order` з ЛР №1–3 перейменовано на `Booking`, а поля — відповідно до теми (клієнт → пасажир, товар → маршрут, кількість → кількість місць, ціна за одиницю → ціна місця). Логіка введення й обробки винятків з ЛР №3 не змінилася.

## Що додано в ЛР №4

Поведінка, яка відрізняється, — **тариф**: одне й те саме бронювання коштує по-різному залежно від того, хто їде.

| Тип | Роль |
|-----|------|
| `Fare` | інтерфейс: `getName()`, `calculateCost(Booking)`; default-методи `requiresDocument()` і `describe(Booking)` |
| `AbstractFare` | абстрактний клас: спільна логіка знижки у відсотках на частину місць і округлення до копійок |
| `FullFare`, `StudentFare`, `ChildFare` | тарифи через `AbstractFare` (0 %, 30 % на одне місце власника квитка, 50 % на кожне місце) |
| `GroupFare` | реалізує інтерфейс напряму: кожне п'яте місце безкоштовне |
| `TicketDesk` | каса — контекст паттерну Strategy |
| `Payable` | інтерфейс «має суму до сплати» |

### Рівень 1
Інтерфейс `Fare` має чотири реалізації. У `Main` створюється масив `Fare[]`, і в циклі для одного бронювання викликається `describe()`: сума різна для кожного тарифу.

### Рівень 2
- **default-метод**: `requiresDocument()` за замовчуванням повертає `false`. `FullFare` і `GroupFare` беруть значення за замовчуванням, а `StudentFare` і `ChildFare` перевизначають його (потрібен студентський квиток або свідоцтво про народження). `describe()` — default-метод, спільний для всіх.
- **абстрактний клас + інтерфейс**: розрахунок «знижка N % на K місць, решта — повна ціна, округлення до копійок» однаковий для пільгових тарифів, тому він один раз написаний в `AbstractFare.calculateCost()`. Підкласи вказують лише відсоток і реалізують `countDiscountedSeats()`. Абстрактний клас тут доречний, бо є спільний стан (`name`, `discountPercent`) і спільний алгоритм. `GroupFare` рахує зовсім інакше (безкоштовне кожне п'яте місце, відсотків немає), тому він реалізує «чистий» інтерфейс.
- **кілька інтерфейсів**: `Booking implements Payable, Comparable<Booking>`. `Payable` — бізнес-поведінка (сума до сплати), `Comparable` — сортування за загальною сумою. У `Main` бронювання сортуються через `Arrays.sort()`, а загальна сума рахується через масив `Payable[]`.

### Рівень 3 — Strategy
`TicketDesk` отримує стратегію `Fare` через конструктор і делегує їй розрахунок ціни. Через `setFare()` тариф змінюється під час роботи програми: користувач вибирає тариф у меню, і той самий об'єкт `TicketDesk` перераховує квиток.

## Запуск

```bash
javac *.java
java Main
```

Сценарій: ввести бронювання (як у ЛР №3) → демонстрація винятків → порівняння тарифів для першого бронювання → сортування → вибір тарифу в циклі (0 — вихід).
